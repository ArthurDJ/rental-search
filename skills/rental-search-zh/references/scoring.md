# 通勤、花费和打分

## 通勤

每个候选都要用地图工具，按用户实际出门的时间实测。房源页上写的时间和直线距离都不是通勤时间。

### 用浏览器里的 Google Maps

1. 用下一个正常工作日（不是节假日），用户出门的时间。
2. 路线链接可以直接带上出发时间，省得去点"出发时间"菜单：

   `https://www.google.com/maps/dir/<origin>/<destination>/data=!4m6!4m5!2m3!6e0!7e2!8j<seconds>!3e0`

   - `<origin>` 和 `<destination>`：带城市和省份的地址，空格写成 `+`，或者 `lat,lng`。
   - `6e0` 表示"出发时间"；`6e1` 表示"到达时间"。
   - `8j<seconds>`：把当地的钟点时间当成 UTC，换算成从 1970 年起的秒数。比如 2026-11-09 08:15，就是 `2026-11-09T08:15:00Z` 这个 UTC 时间戳，等于 1794212100。Python 写法：`int(datetime(2026, 11, 9, 8, 15, tzinfo=timezone.utc).timestamp())`。
   - `3e0` 开车，`3e1` 骑车，`3e2` 步行，`3e3` 公交。
3. 看路线列表。开车时，未来的时间会显示"typically 8–14 min"这样的区间。记下最快那条路线的区间和距离。公交会显示每个方案的时长，记下出发时间之后最快的那个。
4. 确认 Maps 识别出的起点是对的（起点框里会显示完整地址）。用坐标时可能显示成某个商家的名字，只要位置对就没关系。

如果房源很多，可以用脚本读页面文字，比截图快：每个路线块里都有"typically"、时间区间、距离和"via <道路>"。

### 没有确切地址的房源

- 用网站给的坐标（Craigslist 把坐标放在地图元素上，见 `references/sites.md` → Craigslist）、邮编，或者广告里提到的最近路口。
- 结果标"大概位置"。
- 什么线索都没有时，通勤标"未测"，并说明原因。

### 和上限比较

拿区间里**最慢的那头**和上限比。上限 20 分钟，"12–22 min"就意味着路况差的日子会超时，所以这套房最多算**待核实**，表格里用警示色显示。如果用户每周去几天会影响判断，也要说出来。

### 没有地图工具时

估算：直线距离 × 1.35 ÷ 40 km/h（市区开车），并标"估算，非实测"。告诉用户哪几套最需要实测（接近上限的那些）。

## 实际月花费

只看房租会误判："$1,450 水电全包、含车位"可能比"$1,400 水电另付、车位 $100"更便宜。

```
true monthly cost = rent
                  + utilities not included (electricity, heat, water, internet; estimate if not stated)
                  + parking or storage fees
                  + pet fees (if the pets module is on)
                  + one-time non-refundable fees ÷ lease months (move-in fee, admin fee)
                  − free rent ÷ lease months (for example "first month free on a 12-month lease")
```

（实际月花费 = 房租 + 不含的水电网（没写就估算）+ 车位或储物费 + 宠物费（开了宠物模块时）+ 一次性不退的费用 ÷ 租期月数（move-in 费、手续费）− 免租金额 ÷ 租期月数。）

- 押金是退的，不算月花费。单独列出来，因为它影响入住时要准备多少现金。
- 每个估算的部分都要标出来，比如"电费估 $60（未写）"。知道当地的典型数字就用，并写明来源。
- 用户还没定租期时，按 12 个月算，并说明。

## 打分

先过硬性条件，再给通过的房源打分排序。

### 硬性条件

来自需求问卷：城市或区域、房型、必须有的、通勤上限（最慢那头）、开了宠物模块时的宠物政策、用户入住日期固定时的入住日。不满足硬性条件的是**不符合**，并写明原因。页面没写的算**待核实**，不算不符合。

### 分数

默认权重，用户可以改：

| 部分 | 权重 | 怎么算 |
|---|---|---|
| 价格 | 40% | 实际月花费对比预算；等于或低于目标得分最高，到用户说的最高价降为零（没说最高价就按比目标高 30% 算） |
| 通勤 | 20% | 区间最慢那头；到上限得 0 分 |
| 房型 | 15% | 房间数和面积是否适合这家人 |
| 配套 | 15% | 洗衣、车位、家具，以及需求问卷里的加分项 |
| 租约 | 10% | 租期长短和灵活度是否合适，入住日期是否对得上 |

打开模块时，从配套的权重里分一部分给它，或者问用户要不要给它更高的权重（比如公司付钱的住宿，可能最在意能不能开收据和租约条件）。

### 状态

| 状态 | 含义 |
|---|---|
| **符合** | 按页面上的信息，所有硬性条件都满足 |
| **待核实** | 没有不满足的，但至少一个硬性条件取决于没写或互相矛盾的信息 |
| **不符合** | 至少一个硬性条件不满足；写明是哪个 |

已下架的和疑似诈骗的房源放到单独的名单里，附上证据（`references/verification.md`）。

### 解释排序

前 3 名每套给两三条大白话理由，以及要问房东的第一个问题。看起来不错但排得靠后的，用一句话说明拖后腿的地方（"没车位""是 studio""路况差时要 22 分钟"）。
